### 1. CloneSite SQL restore — `csf_6290e08fa8f1132e2c8f07d9`

**Vulnerability: yes.** An on-path attacker can impersonate the configured HTTPS clone server while an administrator or authorized CLI job starts cloning. The initial key-bearing metadata fetch and SQL fallback disabled certificate checks; the resulting downloaded statements reach the database restore loop. Administrator authorization, filename filtering, and a successful download do not authenticate the remote server. Impact is database modification and clone-key exposure, limited by the connected database account's privileges. The original primary wget path did validate certificates, so the insecure metadata/fallback paths are the relevant failures.

**Sensitive file write:** downloaded SQL is written under the clone directory. Arbitrary executable-file writes or OS command execution through SQL require additional server/database privileges and were not established. Medium remains appropriate for the required network position and privileged clone action.

**Correction / compatibility:** [cloneClient.json.php](../plugin/CloneSite/cloneClient.json.php) verifies the metadata fetch, the wget download and the fallback when `shouldVerifySSLCertificates()` is on (off by default). Independently of that setting, the download uses `wget(..., $failOnError = true)`: a failed, stale, error-page or partial dump never enters the restore loop. A redirect makes wget fail and the in-memory fallback follows it. [functions.php](../objects/functions.php) propagates strict verification through streams, cURL, DNS-pinned redirects, and fallbacks; HTTPS redirects cannot downgrade to HTTP. [functionsExec.php](../objects/functionsExec.php) separates quoted command arguments from filesystem paths and checks strict wget failures. Large dumps retain the normal streaming wget path; the pre-existing in-memory fallback remains. CloneSite's SQL transfer stays available.

### 2. BTCPay verification — `csf_e44f1847107c653e0db75627`

**Vulnerability: yes.** A network attacker who can intercept the server's HTTPS marketplace request can forge the response to the public invoice callback. Provider-derived status, amount, and user metadata reach local invoice/payment records and wallet credit. Existing local payment checks do not authenticate that response; accepting a new invoice from the trusted marketplace is intentional provider behavior, not itself an authorization bypass. Impact is forged financial state and marketplace-key disclosure. Medium requires the network position and enabled plugin. **Sensitive file write:** verification responses are logged; wallet/invoice changes are database writes, not arbitrary filesystem writes.

**Correction / compatibility:** [webhook.php](../plugin/BTCPayments/webhook.php) uses verified TLS by default (`shouldVerifySSLCertificates(true)`; `$global['verifySSLCertificates'] = 0` disables it, e.g. for an outdated CA bundle) while keeping the external callback and provider contract. A related, additional concrete leak was corrected: the key-bearing verification URL is now a local variable, so it is absent from the callback's response and serialized response log. Legitimate provider status, amounts, and user metadata retain their existing meaning. Live marketplace behavior is **NOT VERIFIED**.

### 3. BTCPay checkout — `csf_66fc86d80f14eefd35f9a6c0`

### 4. Encoder queue — `csf_567851c082e49f962d7d8a66`

**Vulnerability: yes.** When an upload-authorized user queues media, an on-path attacker can impersonate the configured HTTPS Encoder and receive the Streamer credential and chunk capability, then forge a numeric queue acknowledgement. Upload permissions, administrator-configured destinations, and the existing 2xx/numeric response checks do not authenticate an unchecked TLS peer. Impact is capability/credential disclosure and false queue state; Medium reflects the required network position and queue action. **Sensitive file write:** the request itself writes no sensitive local file; subsequent misuse of exposed credentials requires the receiving route's own privileges and guards.

**Correction / compatibility:** [video.php](../objects/video.php) applies certificate-chain and hostname verification in `postToEncoderQueue()` when `shouldVerifySSLCertificates()` is on (off by default, because the default Docker install uses a generated self-signed certificate for its bundled Encoder). With the option on, an Encoder on the Streamer's own host trusts `TLS_CERTIFICATE_FILE`. Both `Video::queue()` and `sendToEncoder()` use it. The separate Encoder's queue/login source was checked: user/pass, per-job notify URL, Streamer identity, and queue response format remain compatible with multiple Streamers sharing one Encoder. No global single-Streamer token or callback redesign was introduced. Local real TLS handshakes were verified; an actual multi-Streamer encoding/upload workflow and the Encoder's separate outbound transports are **NOT VERIFIED**.

### 11. Payment replay — `csf_2b7daf1f5d1216e822514d87`

**Vulnerability: yes.** A valid signed Stripe/Razorpay delivery can be processed repeatedly through retries or replay; an unsigned arbitrary request still cannot pass the provider signature check. Stripe's timestamp tolerance bounds captured-event replay, but authentic provider retries remain possible. Credit and renewal previously had no durable consumed-payment check. Original-source reproduction of one ten-unit Stripe charge invoked twice produced twenty credited units. Impact is duplicated wallet balance and potentially duplicated subscription fulfillment. High is retained for financial integrity; no universal unauthenticated forgery or unlimited old Stripe-signature lifetime is claimed. **Sensitive file write:** database ledger/subscription writes, not arbitrary sensitive filesystem writes.

**Correction / compatibility:** [YPTWallet.php](../plugin/YPTWallet/YPTWallet.php) processes verified deliveries under a database advisory lock and a transaction. [Wallet_log.php](../plugin/YPTWallet/Objects/Wallet_log.php) uses the existing ledger for durable zero-value `paymentProcessed` markers and recognizes pre-upgrade provider credits. No new schema/migration is required. The credit and its markers commit together; any exception (database, lock, missing wallet) rolls everything back and the IPN answers 500 so the provider retries. The subscription renewal runs inside `YPTWallet::runPaymentStep()`, an SQL savepoint (`SAVEPOINT` / `ROLLBACK TO SAVEPOINT`; `mysqli::rollback($flags, $name)` would roll back the whole transaction): a failed renewal (plan price above the paid amount, plan removed, insufficient balance) is undone alone, the paid credit and the marker are kept, and an error log asks for a manual renewal. Without this, a deterministic renewal failure lost the credit and was retried until the provider gave up (Stripe: up to 3 days; Razorpay: 24 hours, then the webhook is disabled). Nested renewal transfers join the payment transaction; a transfer that fails before writing returns `false` (legacy contract) instead of aborting the payment. Wallet row locking reuses the driver-compatible, fresh `sqlDAL` read in [Wallet.php](../plugin/YPTWallet/Objects/Wallet.php).

[StripeYPT.php](../plugin/StripeYPT/StripeYPT.php) correlates signed event/object IDs and available invoice/charge aliases, so different deliveries of the same charge and related invoice do not pay twice; a later invoice remains a distinct payment. [Stripe ipn.php](../plugin/StripeYPT/ipn.php) preserves signing-secret rotation and reports processing failures as HTTP 500. A `false` from `processSubscriptionIPN()` means "not an AVideo payment" and stays HTTP 200, as before: `isSubscriptionPayment()` matches every `charge.succeeded` without `singlePayment`, including `StripeYPT::setUpPayment()` charges (wallet top-up, PayPerView) that have no customer or metadata. If the subscription is not found, the payer's wallet is credited and an error is logged instead of retrying forever. [Razorpay ipn.php](../plugin/RazorPayYPT/ipn.php) deduplicates by the signed payment body's ID, not an unsigned header; a `subscription.charged` whose notes have no AVideo `users_id`/`plans_id` is acknowledged with 200, as before. Only after successful signature verification does it temporarily enable the existing origin bypass for subscription models; it restores the previous flag afterward. Its real SDK verifier is covered by tests. The separate DiskUploadQuota dispatch remains outside this wallet transaction and retains its integration contract.

**Material limits:** payment processing is serialized per database; lock contention requests a provider retry. Preserve the processed-payment ledger during maintenance. Legacy-credit recognition prevents a second credit but cannot reconstruct a partially completed pre-upgrade renewal; historical fulfillment failures need individual reconciliation. The schema declares wallet/subscription tables as InnoDB; actual deployed engines, real concurrent MySQL/MariaDB deliveries, provider API-version payloads, live renewals, and DiskUploadQuota fulfillment are **NOT VERIFIED**. Alias correlation depends on the relation fields available in the signed provider payload. Stripe API version 2025-03-31 (Basil) removed `invoice.charge`, `invoice.payment_intent` and `charge.invoice` ([changelog](https://docs.stripe.com/changelog/basil/2025-03-31/add-support-for-multiple-partial-payments-on-invoices)); `StripeYPT::getWebhook()` creates the endpoint without `api_version`, so it follows the account default. On Basil or later accounts the `invoice.payment_succeeded` and `charge.succeeded` of one renewal cannot be correlated and both are credited and renewed, exactly as before this patch (confirmed by simulation). Closing it needs a product decision: credit subscriptions only from invoice events on Basil+ payloads, look up `InvoicePayment` through the API, or create the endpoint with a pinned `api_version` (new endpoints only). Socket notifications are not transactional even though database state is.

**Traceability:** every step logs non-secret identifiers (provider, `users_id`, provider payment/event IDs, amount) and the real failure reason: `processPaymentOnce: start | done | already processed, duplicate delivery ignored | FAILED and rolled back ... error=...`, `processSubscriptionIPN: ignored ... | processing ... | renew it manually`, `RazorPayIPN: ...`, `Stripe IPN processing failed ... error=...`. The `paymentProcessed` marker description includes the provider payment ID; markers have value 0 and stay hidden from the user wallet list (`value != 0`). Blockonomics logs txid, address, value and user (public blockchain data), never the callback secret.

## Follow-up review (2026-10-10)

Regressions in the first patch, found by reading the code and confirmed by the tests and simulations above, and fixed:

- **Stripe IPN answered 500 for charges that are not AVideo payments** (`setUpPayment()` charges have no customer/metadata): Stripe would retry them for days. Restored HTTP 200 for "not ours"; real failures still answer 500.
- **A failed renewal discarded a valid payment** and caused endless retries: now isolated in a savepoint (credit kept, error logged).
- **Razorpay answered 500 for subscriptions without AVideo notes**, which disables the webhook after 24 hours: restored 200.
- **Overlong wallet log values aborted the payment** under strict SQL mode (`description` is `VARCHAR(255)`, `json_data` is `TEXT`): `WalletLog::setDescription()` and `setJson_data()` now cut at 255 characters / 65,535 bytes on a UTF-8 boundary. Before the transactional change such a row failed silently after the balance was saved.
- **Pre-existing since commit `34132ad515`:** `transferBalance()` failed when the receiver never had a wallet row (e.g. the site owner receiving renewals), because `getFromUserForUpdate()` replaced the old `getWallet()` that created it on save. The receiver wallet is now created with `Wallet::getOrCreateFromUser()`.
- **Pre-existing on Windows:** `ObjectYPT::cleanCacheName()` split cache names on `DIRECTORY_SEPARATOR` while every name uses `/`, so `clearCache(true)` (home page only) never removed the home page cache. Names are normalized first (no-op on Linux). Fixes `CategoryCacheRegressionTest` together with the test's own separator check.
- Diagnostics restored without secrets (Stripe/Razorpay/Blockonomics/wallet, `on_publish.php`, `aVideoEncoder.json.php`), described in sections 11 and 12.

Provider behavior was checked against the official documentation: [Stripe webhooks](https://docs.stripe.com/webhooks) (signature scheme, 5-minute tolerance, retries up to 3 days, duplicates by event ID and by `data.object` ID + type), [Razorpay best practices](https://razorpay.com/docs/webhooks/best-practices/) (24 hours of retries, disable after 24 hours of failures, 5-second timeout, at-least-once delivery), the [subscription.charged payload](https://razorpay.com/docs/webhooks/subscriptions/), the nginx-rtmp notify source (`app`, `flashver`, `swfurl`, `tcurl`, `pageurl`, `addr`, `clientid`, `call=publish`, `name`, `type`, raw publish args), and [mysqli::rollback](https://www.php.net/manual/en/mysqli.rollback.php). The payment lock can wait up to 10 seconds, longer than Razorpay's 5-second timeout; Razorpay then resends and the marker prevents a second credit.

## Deployment and remaining manual checks

1. Certificate verification for the Encoder, WordPress, CloneSite and SMTP is off by default. Enable "Verify SSL certificates" in CustomizeAdvanced (or `$global['verifySSLCertificates'] = 1`) where those services have valid or privately trusted certificates. For a private CA, configure the PHP stream trust store (`openssl.cafile`/`openssl.capath`), cURL trust store (`curl.cainfo`), and the OS/wget trust store as applicable; the certificate must match the configured hostname. The fixes do not convert intentionally configured HTTP or plaintext SMTP into TLS.
2. CLI backup output now names a private temporary directory. Move successful backups to the operator's private backup storage before OS temporary-file cleanup. Existing public dumps are not relocated automatically. Deploy the 5.2 videos policy; remove or privately relocate legacy CLI dumps, and apply the corresponding filename denial on nginx/IIS/CDN/storage deployments that do not honor Apache `.htaccess`.
3. In a staging payment environment, verify one credit/renewal for repeated and concurrent signed events, a distinct subsequent invoice, retry after failure, renewal failure (credit kept), and InnoDB table engines. Check the Stripe webhook endpoint's API version in the dashboard: on 2025-03-31 (Basil) or later, decide how to avoid crediting both the invoice and the charge of one renewal. Keep processed ledger entries. Third-party DiskUploadQuota needs its own staging fulfillment check.
4. Verify the same-origin series buttons and thumbnail deletion; verify foreign browser origins are rejected. Confirm the existing playlist rename model guard still protects its route.
5. Verify the complete shared-Encoder workflow for multiple Streamers, WordPress login, SMTP delivery, and CloneSite restoration with valid public/private CA chains. These live workflows remain **NOT VERIFIED** by lint, mocks, or the loopback TLS test.
6. If historical secret-bearing diagnostics were shared outside the authorized secret-reader group, address that actual exposure through the deployment's log-retention and credential-rotation procedure. No production log contents were inspected during this review.

Provider retry/deduplication behavior is documented by [Stripe](https://docs.stripe.com/webhooks) and [Razorpay](https://razorpay.com/docs/webhooks/best-practices/). PHP's supported certificate/CA options are documented in [SSL context options](https://www.php.net/manual/en/context.ssl.php). The implementation choices above are this review's assessment of the repository source and compatibility constraints.

Changes are local and uncommitted. No advisory was published, no CVE was requested, and no production service or payment was modified. The simulations used a throwaway MariaDB instance, loopback servers and generated secrets only.
